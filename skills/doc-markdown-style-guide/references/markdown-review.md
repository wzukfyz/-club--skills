# Markdown 文档审查清单（Google Markdown Style Guide）

> 来源: https://google.github.io/styleguide/docguide/style.html | 核对日期 2026-11-21
>
> 本文件可独立使用：每条都自带判据，不需要回读写作档。输出格式固定为
> 「违规项 → 位置 → 规则出处 → 修正建议」。

## G. 审查清单

### 结构（6 条）

- [ ] **G1 全文只有一个 H1**：搜索 `^# `，命中数必须为 1；若为 0 或有多个，报违规。
  *出处 B 节 · 原文 "Use one H1 heading as the title of your document."*
- [ ] **G2 H1 与文件名相同或近似**：`my-doc.md` 对应 `# My doc` 可接受；完全无关则报违规。
  *出处 B 节*
- [ ] **G3 简介存在且 1–3 句**：H1 之后应有独立段落，不做术语解释、不重复标题；超过 3 句可提示精简。
  *出处 B 节*
- [ ] **G4 TOC 位置正确**：若使用目录，必须在简介之后、首个 H2 之前；出现在文末即为违规（读屏
  软件要滚到底才发现）。
  *出处 B 节*
- [ ] **G5 标题层级不跳级**：H1 之后应为 H2，不得出现 H2 → H4；标题文本中仅 H1 用于文档标题。
  *出处 B 节*
- [ ] **G6 每个标题都有显式锚点**：检查标题上一行是否有 `<a id="..."></a>`，id 为小写短横线、
  语义稳定。缺锚点报违规——外部深链会随标题文案变更而断裂。
  *出处 B 节*

### 行文（5 条）

- [ ] **G7 行宽 ≤80 字符**：按 Unicode code point 计（1 汉字 = 1）。仅链接、表格、标题、代码块
  四类可超；链接行超出时，链接**前后**的正文仍须折行。
  *出处 A 节*
- [ ] **G8 无行尾空白**：正则 ` +$` 不得命中；硬换行检查是否为行尾 `\` 而非两个空格。
  *出处 A 节*
- [ ] **G9 中文折行点合法**：折行应落在 `。！？；` 之后，其次 `，、`；在词语中间断开即为违规
  （渲染后出现伪空格）。
  *出处 F 节 · 非 Google 规则*
- [ ] **G10 标题名唯一且完整**：同一文档内不得出现两个同名标题（如两处 `### Summary`）；
  子节标题宜带父级前缀（`### Foo summary`）。
  *出处 A 节*
- [ ] **G11 产品名大小写正确**：`iPhone` 不写成 `IPhone`、`Markdown` 不写成 `markdown`（指产品时）。
  *出处 A 节*

### 列表与代码（5 条）

- [ ] **G12 有序列表用真实编号**：不得出现连续 `1.`；懒人编号已废弃。
  *出处 A 节*
- [ ] **G13 嵌套缩进正确**：嵌套统一 4 空格；编号后 2 空格、项目符号后 3 空格；嵌套层的包裹
  文本为 8 空格。
  *出处 A 节*
- [ ] **G14 代码块全部围栏化且声明语言**：搜索行首四空格缩进的代码块（应为 0 处）；检查每个
  围栏开头是否有语言标识。
  *出处 A 节*
- [ ] **G15 命令行片段已转义换行**：多行命令应在行尾用 `\` 连接，便于整段复制粘贴。
  *出处 E5*
- [ ] **G16 列表内嵌代码块缩进正确**：需相对列表再缩进 4 空格，否则列表会被打断。
  *出处 E5*

### 链接、表格与媒体（5 条）

- [ ] **G17 链接文字有信息量**：不得出现 `[here]`、`[link]`、`[点击这里]`，或把裸 URL 当链接文字。
  *出处 E1*
- [ ] **G18 跨目录不用 `../`**：同目录相对路径可用；出现 `../` 应改为站点绝对路径。
  *出处 E1*
- [ ] **G19 引用式链接用法得当**：仅长链接、重复引用、表格单元格内使用；定义放在首次使用所在
  节末尾（跨节使用则放文末）。短链接被做成引用式也算违规。
  *出处 E2*
- [ ] **G20 表格使用得当**：出现「列多行少」「多列无差异且有空单元格」「格内长段落」任一，
  应改为 H2 小节 + 列表。
  *出处 E3*
- [ ] **G21 图片有替代文本、iframe 显式闭合**：`![]()` 方括号内不得为空；`<iframe ... />`
  自闭合一律报违规。
  *出处 E4*

## H. 易误引的"不存在"规则

| # | 流传说法 | 实际原文/事实 | 处置 |
|---|---|---|---|
| H1 | 长列表用"懒人编号"（连续 `1.`） | 现行原文已改为 `### Use real numbering, even for long lists`，并写明 "This is no longer applicable now that the auto-formatter can keep the real numbers up to date." | 一律用真实编号；不要引用旧版与中文旧译 |
| H2 | Google 要求"一句一行"（one sentence per line） | 原文主张 80 字符硬折行，全文未出现 semantic linefeeds / one sentence per line 的表述 | 一句一行只能作为中文推荐写法（F3），不得标注为 Google 要求 |
| H3 | Google 规定了 TODO 注释格式 | 本指南通篇无 TODO 内容 | 明确回答"本指南无规定"，不要从 C++/Java 注释规范搬运 |
| H4 | Google 规定了中文/CJK 排版 | 原文只讲 `80-character`，未定义 CJK 计量；无中英文空格、全角标点等任何规定 | F 节全部标注为非 Google 规则 |
| H5 | Google 要求 YAML front matter | 原文未提 front matter / YAML / metadata 字段 | 不作要求；项目需要时按项目规范 |
| H6 | Google 规定了文件命名规则（kebab-case 等） | 原文只要求 H1 与文件名 "same or nearly the same"，未规定命名风格 | 不臆造命名规则 |
| H7 | 行尾两个空格是标准硬换行写法 | 原文明确禁止行尾空白，要求改用行尾反斜杠 | 报违规 |
| H8 | 缩进式代码块"更清晰易读"，是 Google 推荐写法 | 原文是让步句："Indented code blocks can sometimes look cleaner in the source, **but** they have several drawbacks"，结论为 "we strongly recommend fencing for all code blocks" | 旧中文译本截断了 but 之后的转折，属断章取义 |
| H9 | `[TOC]` 是通用 Markdown 语法 | 它是 Gitiles 指令；google.github.io 自身用的是 kramdown 的 `* TOC` + `{:toc}` | 按宿主选择方案，见 E6 |
| H10 | Google 规定了表格对齐写法（`:---:`）、badge、emoji、目录深度上限 | 原文均未涉及 | 回答"未规定"，不补充个人偏好 |

## 审查输出格式

```
违规项 N：<规则编号 + 一句话>
位置：    <文件:行号 或 小节名>
出处：    <写作档节号>（原文引句，如有）
修正：    <可直接替换的写法>
```

按 G1–G21 顺序输出；同一规则多处违规合并为一条，逐处列出位置。全部通过时输出
「G1–G21 全部通过」并附行宽、锚点覆盖率的实测数字。
